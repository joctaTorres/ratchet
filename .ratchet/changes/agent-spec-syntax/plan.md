# agent-spec-syntax

## Why

The batch `agent` setting routes lifecycle stages to coding agents by bare name only, so every agent runs its harness-configured default model — a user cannot say `propose: claude:fable` or `apply: opencode:zai/glm-5.2`. This change is the schema boundary of the per-stage-model-selection phase: it widens every string value of the `agent` setting to an `agent[:model]` spec with exactly one pure parser, so validation and parsing can never drift, and so the follow-up `model-flag-threading` change can consume the parsed model without touching config shape.

## What Changes

- `src/core/batch/agent-setting.ts` exports a pure `parseAgentSpec(value)` returning `{ agent, model? }`: split on the **first** `:` (opencode `provider/model` ids and colon-bearing model ids pass through intact); a bare name parses to no `model` key; an empty agent or model part (`:fable`, `claude:`, `:`, ``) throws an error whose message names the offending value. The model part is otherwise free-form pass-through — no model registry.
- Every string position of the `agent` setting — the scalar form and each stage-map value, at both config scopes (project-config `batch.agent` and manifest `settings.agent`) — validates through a single zod refinement on `AgentSettingSchema` that calls that same parser, rejecting malformed specs at config load with the parser's message.
- Existing bare-name configs (scalar, full map, partial map, unset) validate byte-for-byte unchanged; the schema keeps storing whole spec strings, so `scalarAgent`/`resolveAgentForStage` and the nearest-wins per-stage merge are untouched and agent+model move atomically across scopes.
- No engine, adapter, or argv change: implements `features/agent-spec-syntax/parse-agent-spec.feature` and `features/agent-spec-syntax/schema-validation.feature` only. Model-flag emission is the sibling `model-flag-threading` change.

## Design

**One parser, called by the validator (phase-locked decision).** The batch brainstorm locked the syntax: combined `agent[:model]` spec split on the FIRST colon, free-form model pass-through, parsed at the schema boundary. `parseAgentSpec` lives in `agent-setting.ts` because that module already owns the `agent` setting's shape for both scopes (`project-config.ts` and `manifest.ts` both import it, deliberately avoiding the `project-config ↔ batch/config` import cycle — see the module header). The zod refinement calls `parseAgentSpec` rather than re-implementing the split, so "what validates" and "what parses" are the same code path; the engine later calls the same function once per transition.

**Refine the union, not the inner strings.** The refinement attaches to `AgentSettingSchema` (`z.union([z.string(), AgentStageMapSchema]).superRefine(...)`) rather than to each `z.string()` position. Refining inside the union's string branch would bury the parser's message under zod's aggregated `invalid_union` issue; refining after the union means a malformed spec passes the structural check first and then fails with exactly one custom issue carrying the parser's message (with the stage key as the issue path for map values), so config-load errors name the offending value as the phase success criteria require. Both scopes import the same schema, so they cannot diverge.

**Errors name the value, once.** `parseAgentSpec` throws with a message like `Invalid agent spec ":fable": empty agent part (expected "agent[:model]")`; the refinement forwards `error.message` into `ctx.addIssue`. One message source — no duplicated wording between parser and schema.

**Storage stays raw spec strings.** The schema validates but does not transform: resolution (`resolveAgentForStage`) and the cross-scope nearest-wins merge keep operating on whole spec strings, so an override of `apply` replaces agent+model atomically. Splitting stored values into `{agent, model}` objects here would change every consumer's type and break merge atomicity — that is why parsing happens once per transition in the engine (next change), not at storage.

**Agent-neutral by construction (multi-agent-support standard).** The parser never consults the adapter registry and hardcodes no agent name: any agent part is syntactically valid, and unknown-agent rejection stays where it lives today (`UnknownAgentError` in `resolveAdapter`, before any spawn). No skill, command, or generated artifact changes, so there is no per-agent output surface to enumerate.

**Testing (testing standard).** Pure-logic behavior proves at the unit layer — no filesystem, no spawn: extend `test/core/batch/agent-setting.test.ts`, which already exercises the shared schema through both scopes (`ProjectConfigSchema.shape.batch` and `BatchSettingsOverrideSchema`) via a scope table. New tests mirror the two `.feature` files in their headers per the repo convention. The full suite and the enforced `COVERAGE_THRESHOLD` gate must stay green; new branches in `agent-setting.ts` are fully covered at the unit level.

**Documentation (documentation standard).** This change alters a user-facing config surface (accepted values of `batch.agent` / manifest `agent`), so the Reference doc must move with it in this change: `docs/configuration/config-yaml.md`'s `agent` entry and its validation subsection gain the `agent[:model]` spec form, the first-colon rule, and the empty-part config-load rejection — describing actual post-change behavior only (a named model is validated and stored; flag emission is documented by the sibling docs change when it becomes real). `README.md` does not describe the agent value grammar today, so it needs no edit here; the phase's `model-selection-proof-and-docs` change owns the full README/docs syntax write-up once the behavior is end-to-end. No core flow changes shape, so no new Mermaid diagram is required — the existing doc structure is updated in place.

Not applicable here: `delegated-lifecycle` (no lifecycle instructions or spawn prompts touched), `generalizable-defaults` (no defaults shipped into consuming repos — the parser is internal validation), `instruction-fed-config` (no skill reads config; no instructions-payload change).
