# config-write-load-honesty

## Why

`ratchet batch config --set agent=<value>` persists any string (`validateSetting` has no `agent` check), so the write path happily stores `agent: "claude:"` — a value the very next config load rejects (PR #95 review finding 3). And when the load does reject it, `readProjectConfig` prints the generic `Invalid 'batch' field in config (check gate/strategy/proofOfWork values)` — never naming `agent` or the offending value — and silently drops the ENTIRE batch section, reverting valid gate/locus/permissions siblings to defaults (finding 2). Both boundaries must become honest: the write path refuses what the loader rejects, and the load path names the actual failing key(s)/value(s) while preserving valid siblings.

## What Changes

- `validateSetting` (`src/core/batch/config.ts`) gains an `agent` branch that validates the value through `AgentSettingSchema` (whose `superRefine` routes every string position through `parseAgentSpec`): a scalar value is validated as a spec string; a value starting with `{` is parsed as a YAML flow map and validated as a stage map, so per-stage entries are checked too. Failures return `ok: false` with an error naming the offending value (and the stage key for map entries). Implements `features/config-write-load-honesty/write-path-validation.feature`.
- `SetResult` gains an optional `parsedValue` carrying the typed agent value (string or stage map). `setProjectBatchSetting` persists it (a map is written as a real YAML map, not a quoted string, mirroring how `port`/`insecure` persist their real types), so what the write path stores is exactly what the loader accepts. `resolveChangeStepSettings` assigns `parsedValue` for the `agent` override, so a malformed standalone `--agent` now fails inside `validateSetting` with a message naming the value, before any spawn.
- `readProjectConfig` (`src/core/project-config.ts`) replaces the whole-section `safeParse` of `batch` with per-key validation over the batch schema's shape: each present key is safeParsed independently; valid keys are kept; each failing key is dropped with a warning naming the key path (e.g. `batch.agent`, `batch.agent.apply`) and the offending value, derived from the zod issues — replacing the generic gate/strategy/proofOfWork text. Implements `features/config-write-load-honesty/load-path-warning.feature`.
- `test/batch-engine/agent-model-selection.test.ts` (the phase proof) replaces the hand-rolled YAML re-parse scenario (`ProjectConfigSchema.shape.batch.safeParse` over a self-parsed file) with scenarios that drive `readProjectConfig` and `setProjectBatchSetting` over the tmpdir fixture. Implements `features/config-write-load-honesty/e2e-real-seams.feature`.
- Reference docs: `docs/commands/batch.md` (`batch config` settable-keys table and `--set` behavior: agent spec validation, inline stage-map form, reject-without-write), `docs/configuration/config-yaml.md` (load behavior on an invalid batch key: per-key warning naming key path and value, valid siblings preserved), and the README's batch-config/malformed-spec sentences where they describe the stale generic behavior.
- Not breaking for valid configs: all pre-fix valid scalar specs, bare names, and hand-authored stage maps load and write byte-for-byte unchanged. Configs that previously "wrote fine" with a malformed agent value now fail at write time naming the value — the intended honesty fix.

## Design

- **One validation authority, reused at the write seam.** The write path validates through `AgentSettingSchema` (hence `parseAgentSpec`) — the exact schema the loaders use — not a re-implementation, so write and load can never diverge again. The zod issues already carry the parser's value-naming messages (proven by the sibling `spec-parser-hygiene`); the write path just formats them as `agent<.stage>: <message>`.
- **Inline stage maps: `{`-prefix rule, never blind YAML.** A `--set agent=` value is treated as a stage map ONLY when it starts (after trim) with `{`, parsed as YAML flow syntax. Blind-YAML-parsing every value would misread the malformed scalar `"claude: opus"` as a map `{claude: opus}` and break the phase success criterion (`batch config set agent "claude:"` must fail as a scalar naming the value — YAML would read it as `{claude: null}`). With the prefix rule, all non-brace values stay scalars and hit `parseAgentSpec` directly. An unparseable or non-object `{...}` value fails with an actionable message naming the value. This also closes today's silent trap where `--set agent={apply: opencode}` persists the map as a quoted STRING that the loader then rejects — map input now either persists as a real map or is refused.
- **Load path: per-key resilience instead of whole-section drop.** `readProjectConfig` already validates top-level fields independently ("resilient field-by-field validation"); this change pushes the same philosophy one level down into `batch`: iterate the batch schema shape's keys, safeParse each present value, keep the valid ones, and warn per failing key with `batch.<key>[.<path>]` plus the offending raw value (JSON-stringified, secrets excluded: `authToken` is never echoed — its warning names the key only). Preserving valid siblings is chosen over "drop the section but say so" because it matches the file's existing resilience contract and the finding's harm was precisely the silent revert of gate/locus/permissions. Unknown keys in the section remain ignored (the schema is `.partial()`, not `.strict()`) — unchanged, out of scope.
- **Scope guard vs. sibling change.** The structured "actionable error" contract for the standalone `--agent` CLI surface (finding 4) belongs to the sibling `standalone-agent-flag-error`. This change only makes `validateSetting` reject malformed agent values (so `resolveChangeStepSettings` throws a value-naming Error before any spawn instead of a deep raw throw) and keeps the assignment typed via `parsedValue`; how the command layer renders that failure is the sibling's contract. The `eval` section's generic warning has the same shape but is not a finding — untouched.
- **Multi-agent standard:** all new messages stay agent-neutral (they echo whatever agent/spec string the user wrote and hardcode no agent name); validation consults only the shared schema, never the adapter registry. No agent-facing generated surface changes, so no per-agent outputs are involved.
- **Testing standard (`testing` tag), pyramid placement:** `validateSetting`/`setProjectBatchSetting`/`resolveChangeStepSettings` coverage is unit/integration-layer in `test/core/batch/config.test.ts` (tmpdir fixture for the write tests); `readProjectConfig` per-key behavior is unit-layer in `test/core/project-config.test.ts` (existing tmpdir + console.warn-spy patterns); the command surface (`--set agent=claude:` fails, file untouched) extends `test/commands/batch/config.test.ts`; and the phase proof `test/batch-engine/agent-model-selection.test.ts` proves ONLY what the unit layers cannot — the real load/write seams over the fixture — replacing the hand-rolled re-parse. Nothing is pushed up the pyramid; the full suite and coverage gate stay green.
- **Documentation standard (`documentation` tag):** reference-doc updates are a mandatory task below (docs/commands/batch.md, docs/configuration/config-yaml.md, README.md). No new diagram: both touched surfaces are existing leaf reference sections (a settable-keys table and a config-load behavior note), not a core-flow change.
