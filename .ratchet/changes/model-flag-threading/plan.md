# model-flag-threading

## Why

`agent-spec-syntax` made every string value of the `agent` setting accept an `agent[:model]` spec, but the engine still hands the stored spec string straight to `resolveAdapter`, so a spec like `apply: opencode:zai/glm-5.2` would be rejected as an unknown agent and the named model never reaches the spawned process. This change threads the parsed spec through the engine and adapters — the second slice of the per-stage-model-selection phase — so a named model actually lands on the spawned agent's argv via that agent's own model flag.

## What Changes

- `src/core/batch/engine/engine.ts` `buildSpawnRequest` parses the resolved spec once per transition through `parseAgentSpec`, resolves the adapter by the **agent part** (an unknown agent part still throws `UnknownAgentError` before any spawn, naming `rex`, not `rex:some-model`), and hands the model part to the adapter via the request context. Implements `features/model-flag-threading/engine-spec-parsing.feature`.
- `src/core/batch/engine/agent.ts`: `AgentRequestContext` gains an optional `model?: string`; the `AgentAdapter` interface gains an optional readonly `modelFlag?: string` capability declaration; `CommandAgentAdapter` takes `modelFlag` as a **required** constructor parameter (claude/opencode/cursor `--model`, codex/gemini `-m`) and `buildRequest` appends `[modelFlag, model]` after the base argv, before the permission flags, **only** when `context.model` is set — no model, byte-for-byte today's argv. Implements `features/model-flag-threading/model-flag-argv.feature`.
- The remaining consumers that treat the resolved value as an agent id resolve through the spec's agent part so a spec-form value routes exactly like its bare name: `src/core/batch/engine/instructions.ts` (`rctInvocation`, the decompose invocation, `rctPrOpenInvocation`) and `src/core/batch/engine/skill-locus.ts` (`ensureCommandInSpawnLocus`). A spec-form stage value gets the mapped agent's own invocation syntax and its spawn-locus guarantee, never the default agent's or a synthetic-agent skip.
- The registry drift guard (`test/core/batch/agent-init-link.test.ts`) additionally asserts every spawnable adapter declares a non-empty `modelFlag` and emits exactly that flag when a model is set.
- No config-shape, resolution, or merge change: `resolveAgentForStage`/`scalarAgent` keep returning whole spec strings (nearest-wins merge stays atomic over agent+model). No README change (owned by the sibling `model-selection-proof-and-docs` change); `docs/configuration/config-yaml.md` gains the flag-emission behavior that becomes real here.

## Design

**Parse at the last resolved boundary, once per transition (phase-locked decision).** The batch brainstorm locked parsing at the schema boundary and threading in the engine: storage and merge stay whole spec strings, and `buildSpawnRequest` — the single point every spawn path funnels through (change transitions, decomposition, PR step) — is where the resolved string becomes `{agent, model}` via the same `parseAgentSpec` the schema refinement validates with. Config load already rejected malformed specs, so the engine-side parse cannot throw on validated config; there is deliberately no second validation layer. The `RATCHET_BATCH_AGENT_CMD` override branch returns before any resolution, unchanged, so e2e/eval determinism is untouched.

**Adapter resolution by the agent part keeps `UnknownAgentError` early and exact.** `buildSpawnRequest` resolves `resolveAdapter(spec?.agent, this.adapters)`: an unregistered agent part still throws before any spawn, and the error names the agent (`rex`), not the full spec — the model part is never what makes an agent unknown. An unset agent resolves `undefined` → `DEFAULT_AGENT` exactly as today.

**The model rides `AgentRequestContext.model`; adapters own their flag.** `buildSpawnRequest` passes `{ ...context, model: spec?.model }` to `buildRequest`. The context is the right vehicle because it is already the narrow, structural slice adapters may read (`ResolvedStepContext` stays assignable); adding a parameter to `buildRequest` would churn every implementor and caller for one optional value. Each `CommandAgentAdapter` declares its `modelFlag` as a required constructor parameter — an adapter cannot be registered without stating its flag, which is what makes the drift guard meaningful — and the flag lives next to the base argv the adapter already owns (locked decision: no model-flag registry in `config.ts`; `AI_TOOLS` stays about init/binaries). `buildRequest` appends `[this.modelFlag, context.model]` between the base argv and the permission flags: base argv shape is preserved for parsers of leading flags, and permission flags remain the trailing block they are today. With no model set the argv assembly touches nothing — byte-for-byte identity is the success criterion, proven by keeping the existing argv assertions green unmodified.

**Every agent-id consumer resolves through the agent part — no raw-spec leaks.** Besides the spawn, three call sites treat the resolved value as an agent id for the command-generation registry: the `/rct` invocation token builders in `instructions.ts` and the spawn-locus guarantee in `skill-locus.ts`. Left unparsed, a spec-form value would silently fall back to `DEFAULT_AGENT`'s invocation syntax (handing opencode a claude-style `/rct:` token) or skip the locus guarantee as a "synthetic agent" — violating the multi-agent-support standard's rule that shared paths never favor one agent. Each site parses the agent part with the same `parseAgentSpec` before the registry lookup; the synthetic-agent skip in `skill-locus.ts` still applies only to genuinely unregistered agents (test fakes), which parse as bare names unchanged.

**Agent-neutral by construction (multi-agent-support standard).** No shared code path special-cases an agent name: the flag is a per-adapter declaration, the renderer/locus logic keys on parsed agent ids exactly as before, and all five registered agents get their flag in this change (enumerated per-agent surface: the `modelFlag` declarations for claude, codex, gemini, cursor, opencode in `BUILTIN_ADAPTERS`). No skill, command, or generated artifact changes, so there is no per-agent file-generation surface.

**Testing (testing standard).** All behavior proves at the unit level over in-memory inputs — no filesystem, no spawn:
- `test/batch-engine/agent.test.ts` (header gains `model-flag-argv.feature`): per-adapter model-flag argv (all five, via the Scenario Outline table), no-model byte-for-byte argv (existing assertions stay green unmodified), and model-flag-before-permission-flags ordering alongside `permission-flags-in-argv.test.ts` conventions.
- `test/batch-engine/agent-stage-routing.test.ts` or a sibling engine unit (header gains `engine-spec-parsing.feature`): `buildSpawnRequest` via injected fake adapters — spec-form stage value resolves the mapped adapter and the captured `AgentRequestContext.model` is the exact model string; bare name and unset agent capture no model; `rex:some-model` throws `UnknownAgentError` naming `rex` with no spawner call.
- `test/batch-engine/instructions.test.ts` and `test/batch-engine/engine-skill-locus.test.ts`: spec-form values render the mapped agent's invocation token / resolve its command adapter.
- `test/core/batch/agent-init-link.test.ts` (drift guard): every spawnable adapter declares a non-empty `modelFlag`, and `buildRequest` with a model appends exactly `[modelFlag, model]`.
The full suite and the enforced `COVERAGE_THRESHOLD` gate stay green; new branches in `engine.ts`/`agent.ts` are fully covered at the unit level. The phase's integration proof (`test/batch-engine/agent-model-selection.test.ts`) is owned by the sibling `model-selection-proof-and-docs` change, not here — nothing in this change may be pushed up the pyramid into it.

**Documentation (documentation standard).** This change makes flag emission real, so the Reference doc moves with it: `docs/configuration/config-yaml.md`'s `agent[:model]` spec subsection gains the behavior that a named model is passed to the spawned agent via that agent's model flag (claude/opencode/cursor `--model`, codex/gemini `-m`) and that a bare name emits no flag so the agent's harness-configured default model applies — actual post-change behavior only. `README.md` needs no edit here: it does not describe the agent value grammar, and the full user-facing syntax write-up (README + docs) is owned by the sibling `model-selection-proof-and-docs` change. No core flow changes shape (the spawn pipeline is unchanged, one value is threaded through it), so the existing doc structure is updated in place with no new Mermaid diagram.

Not applicable here: `delegated-lifecycle` (no lifecycle instruction content or spawn prompts change — only which adapter renders the token), `generalizable-defaults` (no defaults shipped into consuming repos), `instruction-fed-config` (no skill reads config; the instructions payload's shape is unchanged).
